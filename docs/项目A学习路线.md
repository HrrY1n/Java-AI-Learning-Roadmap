# 项目 A 学习路线：校园预约与资源管理系统

项目 A 的正式定义、版本表（A0–A6）与"单体优先"原则见 [统一学习路线](../统一学习路线.md#项目-a校园预约与资源管理后端)。本文件回答一个更早的问题：**在 Stage 05 数据库开始之前，这个项目怎么随 Stage 01–03 逐级生长**。

## 定位与边界（先读）

- Stage 01–03 期间的一切预约相关代码都属于**预研练习**：练当前 Stage 的概念，顺便让未来项目 A 的业务边界在脑子里成形。它**不是**项目 A 本身，不计入简历项目。
- [学习执行计划](../学习执行计划.md) 的 CURRENT 才决定现在写不写代码。当前 CURRENT 是"完成 Stage 01 验收，不开后续项目代码"——所以本文现在**只提供路线与需求，不提供骨架代码**；每级预研到达对应 Stage 时，再由你按"必要的最小骨架"自行创建（需要骨架需求时向 AI 要"需求澄清"而不是"代写"）。
- 预研代码放对应 Stage 的 `my_practices/`（如 `stages/stage01_java_basics/my_practices/booking_console/`），package 用 `com.javaroadmap.stageNN.practices.booking...`。

## 业务最小边界

校园预约系统的核心一句话：**用户预约某个资源在某个时段的使用权，冲突则失败，可取消。**

最小名词表（随 Stage 逐步实体化，不要提前扩表）：

| 名词 | 最小字段 | 不做什么 |
| --- | --- | --- |
| User | id、姓名、角色（学生/管理员） | 注册登录、密码加密（Stage 06 认证才做） |
| Resource | id、名称、类型（会议室/自习位）、容量 | 多校区、审批流 |
| Booking | id、user、resource、日期、开始/结束时间、状态（有效/已取消） | 周期预约、提醒通知 |

冲突规则只有一条：同一资源在重叠时段只能有一张有效预约。

## 预研 P1（Stage 01）：控制台预约菜单

**用的知识**：变量、分支、循环、数组、方法、Scanner（正是 Stage 01 验收清单要求的菜单/数组/方法综合）。

**需求**（进入该阶段时实现）：

1. 预置一个资源数组（如 3 间会议室）与一个预约记录数组（平行数组：资源下标、用户名、时段编号，上限 20 条）。
2. 菜单：1 查看资源 / 2 提交预约 / 3 查看全部预约 / 4 取消预约 / 0 退出。
3. 提交预约时检查：资源存在、时段合法（1~8 节）、该资源该时段是否已被有效预约——冲突则提示失败。
4. 非法输入不崩溃（Scanner 防御模式）。

**验收标准**：正常预约成功并出现在"查看全部"；同一资源同时段第二次预约失败；取消后再预约成功；非法菜单项与非数字输入均不崩溃。

**刻意不做**：用对象（那是 P2）；文件存储（那是 P3）；"查找效率"讨论（数据量 20，感受不到——但记下这个直觉）。

## 预研 P2（Stage 02）：对象建模版

**用的知识**：类、构造器、封装、多态/接口、Entity/Service 分层。

**演进需求**（在 P1 代码基础上重写，不保留平行数组）：

1. `User`、`Resource`、`Booking` 三个 Entity：字段 private、构造器校验（时段编号 1~8、id > 0）。
2. `Booking` 承载自身规则：`isActive()`、`cancel()`（重复取消必须失败）。
3. `Resource` 承载冲突判断：`conflictsWith(Booking other)`。
4. `BookingService`：提交（含冲突检查）、取消、按用户查询——**Service 不出现 Scanner/println**。
5. 入口菜单只做组装与展示。

**验收标准**：P1 的全部验收项仍然成立；另外：Service 层无控制台代码；重复取消返回失败；能指着代码说出"每条业务规则住在哪个类里、为什么"。

**刻意不做**：继承体系（不要造 `Room extends Resource`——先问"有什么行为差异值得多态"，答不出就不用继承，见 Stage 02 继承与组合深化课）。

## 预研 P3（Stage 03）：集合 + 文件持久化 + Repository

**演进需求**：

1. 数组/平行数组全部换成集合：预约记录用 `List<Booking>`；"资源 id → 预约列表"的冲突查询考虑 `Map<Integer, List<Booking>>`（用 [集合选择深化课](../stages/stage03_java_core/deep_dives/01_choose_collection/README.md) 的方法论证选择）。
2. 提炼 `BookingRepository` 接口（save/findByResourceId/findActiveAll/cancel…），实现内存版与 UTF-8 文件版（格式自定，CSV 即可），启动加载、变更写回。
3. 业务异常与失败表达：冲突提交 → `Result.fail`；文件损坏行 → 明确策略（跳过并提示，或失败，写清理由）。
4. 用 Stream 提供"某用户的有效预约"查询；与 for 版对照后择一保留。

**验收标准**：P2 全部验收项成立；删除程序重跑，数据仍在；构造一条损坏行程序不崩溃且行为符合你的既定策略；`BookingService` 换 Repository 实现时零改动。

**刻意不做**：MySQL（Stage 05）、排序/分页（数据量不需要）、并发（单进程顺序执行）。

## 与正式项目 A 的衔接

| 预研产物 | 进入 Stage 05 后的去向 |
| --- | --- |
| P1–P3 沉淀的业务名词与规则 | A0 的需求边界与表设计输入（User/Resource/Booking 三张表 + 冲突约束） |
| `BookingRepository` 接口与"读-改-写"文件实现 | 换成 MySQL 实现后，文件版留作测试替身；"读全量-改-写全量"的低效感将成为理解索引与 SQL 条件更新的动机 |
| 冲突判断 `conflictsWith` | 变成 SQL 的重叠区间查询与唯一约束设计 |
| `Result`/异常分层 | 变成统一异常处理与事务回滚边界的讨论素材 |

进入 Stage 05 时，把预研目录归档（保留为过程证据），正式项目按 [统一学习路线](../统一学习路线.md) 的 A0 重新建库建表——**预研代码不直接搬进项目 A**，搬的是理解。
