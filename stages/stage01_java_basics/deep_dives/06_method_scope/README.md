# 深化课 06：方法、作用域与"一个方法一件事"

对应示例：`com/javaroadmap/stage01/deepdives/methods/MethodScopeDemo.java`

**运行后你会看到什么**：4 行输出。看完本文你应该能解释"局部变量为什么出了方法就不存在"，并有一套可操作的"要不要拆方法"判断法。

## 场景

方法拆多了觉得碎片化，不拆又回到"main 三百行"。day06 的答案文件里 `getTotal/findMax/...` 拆得漂亮，但"为什么要这么拆"没人讲。本课把标准讲清楚：**作用域决定了拆分是安全的，单一职责决定了拆分是有用的**。

## 必须理解

**作用域（scope）**：变量只在声明它的 `{}` 块内有效。方法每次被调用，JVM 都新建一块独立的局部变量区（术语叫栈帧）；方法返回，整块销毁。推论：

- 不同方法可以有同名局部变量（两个方法里都有 `sum`，互不相干）；
- 方法之间传递数据只有两条正规通道：**参数（进）和返回值（出）**；
- 参数也是局部变量——结合 [深化课 04](../04_argument_passing/README.md) 的值传递，就完整了。

**字段 vs 局部变量**：声明在方法外、类内的变量（示例的 `callCount`）属于类，所有方法共享，活得比任何一次调用都久。它是跨方法共享状态的唯一简便手段——也因此危险：任何方法都能改它。初学规则：**优先用参数和返回值传递数据，字段只留给确实需要"跨调用记住"的状态**（如调用计数）。

## 理解原理："一个方法一件事"怎么判断

三个可操作的检查（按顺序问）：

1. **一句话测试**：能用一句不含"然后"的话描述这个方法吗？"打印评语"可以；"算平均分然后打印评语"不行——拆。
2. **修改理由测试**：未来哪类需求变化会迫使你改这个方法？如果两个变化的理由经常同时出现（改评语规则 + 改打印格式），说明职责纠缠，拆开。
3. **层级测试**：main 只应做"流程编排"（取输入 → 调用 → 汇总输出），具体计算下沉。示例里 `describe` 调 `grade`、`main` 只调 `describe`，每层向下依赖、不越级。

拆得过碎同样是坏味道：两行的小方法若只被调用一次且无独立语义，合并更易读。**拆分的目的是可理解与可复用，不是行数**。

**Observe（先预测再运行）**：预测 4 行输出的值（注意 `callCount` 在两次 describe 后的变化）；取消被注释的那行会怎样——先预测错误类型再验证。

## 动手：修改一个条件

1. 把 `grade` 里 `>= 90` 改成 `> 90`：需要改几个方法？答案是"只改一个"——这正是拆分的收益，改动被隔离在单一职责内。
2. 给 `add` 增加第三个参数重载 `add(int a, int b, int c)`：两个同名方法共存叫**重载**（P1 了解即可）；JVM 按参数类型与个数区分它们。

## 常见错误

- 用字段代替参数传值：方法变成"只能按固定顺序跑"的暗耦合（`a()` 必须在 `b()` 前调用），流程一旦变化就碎。
- 在循环里声明方法试图"复用"：方法必须声明在类中；循环里该复用的是**调用**。
- 返回值没接收：`add(3, 4);` 单独一行合法但计算结果被丢弃——不是 bug 就是冗余。

## 独立练习

在 `my_practices/` 写 `ScoreReport`：读入一组成绩（数组写死即可），输出总分、平均分、最高分、及格率（百分比，一位小数）。硬性要求：main 只做流程编排（不超过 10 行）；每个统计一个方法；不使用任何类级字段。完成后回答：如果"及格线"从 60 改成 50，你改了几处？
