# 深化课 02：整数除法与类型转换——为什么平均分总是错的

对应示例：`com/javaroadmap/stage01/deepdives/integertype/IntegerDivisionDemo.java`

**运行后你会看到什么**：11 行编号输出。看完本文你应该能准确预测其中每一行的值，并能解释 day05 里 `sum * 1.0 / scores.length` 中 `* 1.0` 为什么不可省略。

## 场景

三个成绩 95、76、82，平均分明明是 84.33…，程序却输出 84。更糟的是：语法完全正确、编译不报错、大多数测试数据下结果"看起来也对"（比如 90、90、90 时输出 90.0 一样的 90）。这类错误不靠编译器，只能靠理解规则。

## 必须理解

Java 的规则一句话：**两个 `int` 运算，结果还是 `int`——除法只保留整数部分，直接丢弃小数（不是四舍五入）**。

由此推出判断方法，看操作数类型，不看变量存的值：

- `int / int` → 整数除法（丢小数）
- `int / double` 或 `double / int` → 另一方被自动"提升"为 double，做小数除法
- `double / double` → 小数除法

所以 `10 / 3` 是 3，`10 / 3.0` 是 3.333…——同一个除号，行为取决于**写出来的字面量类型**。

**心智模型**：把每个运算符想成一台机器，机器只认标签不认数值。`a / b` 交给"整数除法机"还是"小数除法机"，由 a、b 的类型标签决定；值只是原料。

## 理解原理

**强制转换 `(int)` 是截断**：`(int) 3.99` 得 3，`(int) -3.99` 得 -3（向零取整）。四舍五入要用 `Math.round`（返回 `long`，还要再转 `int`）。

**转换的位置决定含义**——示例第 10、11 行是最容易混的一对：

```java
(double) (a / b)   // 先整数除法得 3，再转 double → 3.0，小数已经回不来了
(double) a / b     // 先转 a 为 10.0，再做小数除法 → 3.333…
```

括号改变了"谁先发生"。转换不能恢复已经丢弃的信息，只能改变接下来的运算方式。

**Observe（先预测再运行）**：运行前把 11 行输出逐行写在纸上，特别是第 5、9、10、11 行；运行后对不上的行，回到规则解释"我错在哪一步"。

## 常见错误

- `(int) 3.99` 以为得 4：截断不等于四舍五入。
- `sum / length` 得 84 后想"再转 double 补回来"：信息已丢，无能为力。
- 用 `* 1.0` 修复时写成 `(int) sum * 1.0 / count`：转换只作用于紧邻的那个操作数（本例恰好无害，但说明你没理解优先级，换一组数据就会出错）。

在 `my_practices/` 写一个 `PriceSplitter`：输入商品总价（整数，单位分）和人数，输出每人应付金额，保留两位小数（用 `String.format("%.2f", x)`）。要求分别用"只除 int"和"先转 double 再除"两种写法实现，并在注释里写明哪种正确、为什么。
