# 深化课 01：List / Map / Set——按"怎么访问数据"选择结构

对应示例：`com/javaroadmap/stage03/deepdives/collectionchoice/CollectionChoiceDemo.java`

**运行后你会看到什么**：5 行输出，覆盖三种结构的典型用法。看完本文你应该能对任意需求说出"用哪个、为什么"，并预测 `map.get(不存在的键)` 的行为。

## 场景

day01–day03 分别学了三个集合的 API。但真实写代码时遇到的问题是反过来的："我要存一批学生，该用什么？"——答案不取决于学生是什么，取决于**之后怎么找回它们**。选择错误不会编译失败，只会在数据变大后变成性能问题或去重 bug，所以必须在选择时就分清。

## 必须理解

选择只看一个问题：**数据将来怎么被访问？**

| 访问方式 | 选择 | 典型复杂度（Stage 04 会量化） |
| --- | --- | --- |
| 按位置 / 按插入顺序，允许重复 | `ArrayList` | `get(i)` 直达；`contains(x)` 逐个比对 |
| 按唯一标识直接定位 | `HashMap` | `get(key)` 常量级直达 |
| 只关心"有没有"，自动去重 | `HashSet` | `contains` 常量级；无顺序 |

三个反例帮助记忆：

- 用 `List` 存"姓名→成绩"然后线性查找：数据到十万条，每次查询十万次比对——这就是 day02 HashMap 示例注释里说的场景。
- 用 `Map` 存"签到记录"：键重复会**覆盖**旧值，去重语义被静默吞掉。
- 需要"按添加顺序展示"却用 `HashSet`：顺序不保证，输出随机。

**心智模型**：List 是**队伍**（有位置、可并列）；Map 是**门牌簿**（名字→房号，直达）；Set 是**签到表**（同一名字只出现一次，出现顺序不作承诺）。

## 理解原理：Map 的"直达"从哪来

`HashMap` 对 key 计算 hash 值，直接定位到存储桶，再比对 key 确认——因此"找"的代价与数据量基本无关。代价是两条纪律：

1. **key 必须稳定**：对象做 key 后又被修改（改了参与 hash 的字段），就再也找不到它。
2. **顺序无承诺**：需要顺序时要么换 `LinkedHashMap`/`TreeMap`（P1），要么显式排序。

`get(不存在的键)` 返回 **null 而不是报错**——null 会在你使用它的那一刻变成 `NullPointerException`。防法：用 `containsKey` 先判断，或 P1 的 `getOrDefault`。这也是 [异常设计深化课](../03_exception_design/README.md) "null 与异常" 取舍的入口案例。

**Observe（先预测再运行）**：预测 5 行输出，特别是第 3 行与第 4 行。

## 动手：修改一个条件

1. 场景 C 里把 `HashSet` 换成 `ArrayList` 再 add 两次 "S001"：输出变什么？这个差异就是"去重该谁负责"的答案（Set 负责，还是你自己写代码保证）。
2. 场景 B 里再 `put("小明", 88)`：Map 的"键唯一"表现为覆盖旧值——同键重复 put 不报错，这是新 bug 的常见来源。

## 常见错误

- 遍历 `HashMap` 时期望插入顺序。
- 用可变对象当 key 后又修改它。
- `map.get(k)` 直接 `.xxx()` 链式调用，null 一路传到底。
