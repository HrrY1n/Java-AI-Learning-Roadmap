# synchronized、可重入性与死锁防线

> 对应示例：`day03_synchronized_mutex/App.java`

## 1. 监视器锁（Monitor）与 JMM 语义

Java 每个对象都可以当作一把锁。进入 `synchronized(lock)` 先获取锁、离开（无论正常结束还是抛异常）自动释放锁。

- **双重保证**：不仅在同一时刻只许一条线程进临界区（保证原子性），根据 JLS §17.4.5 **监视器锁规则**：对同一把锁的 `unlock` 操作 **happens-before** 后续另一线程对**同一把锁**的 `lock` 操作——这意味着前一个线程在临界区内的修改对后一个线程天然可见！
- **必须抢同一把锁**：读与写双方必须锁同一个对象。如果 `increment` 锁 `lock`、另一方锁 `otherLock`（或一个锁静态方法、一个锁实例方法），两边互不阻塞，竞态立刻回来。

| 写法 | 实际锁住的对象 | 彼此是否互斥 |
| --- | --- | --- |
| `synchronized void foo()`（实例方法） | `this`（当前对象实例） | 同一实例的多个实例方法互斥；不同实例互不阻塞 |
| `static synchronized void bar()`（静态方法） | `Class` 对象（如 `Account.class`） | 全类共享这把类锁；**与实例锁 `this` 互不互斥！** |
| `synchronized (lock) { ... }` | 括号里指定的任意锁对象 `lock` | 粒度最细、最可控，工程中最常用 |

## 2. 锁的可重入性

当一个线程已经持有了 `this` 锁（进入 `ReentrantCounter.addAndLog()`），在方法内部再次调用同对象的 `synchronized void recordLog()` 时，JVM 发现当前线程就是锁的主人，直接让**持锁计数 +1** 并放行；退出内层计数 -1，直到归零才真正释放锁。没有可重入性，面向对象里“一个加锁方法调另一个加锁方法”就会立刻把自己卡死。

## 3. 最小死锁模型与预防

```text
线程 1 拿着锁 A，等待锁 B；
线程 2 拿着锁 B，等待锁 A。  ──▶ 双方永远等下去，CPU 占用 0% 却卡死不动（Deadlock）
```

**工程预防第一原则（统一加锁顺序）**：如果需要同时拿两把以上的锁（如账户 A 给账户 B 转账），所有线程必须按固定全局顺序加锁（例如始终先锁 `id` 较小的账户、再锁 `id` 较大的账户），从根上打破循环等待。

## 学习验收与自我检核

- **需要掌握什么**：判断不同 `synchronized` 写法锁住的是哪个对象；理解可重入锁机制与 `unlock` happens-before `lock` 语义；解释并预防两把锁交叉导致的死锁。
- **如何证明理解**：① 看到一个类里既有 `static synchronized` 又有普通 `synchronized` 方法时，立即判定两方法并发调用不互斥；② 解释为什么 `SafeCounter.get()` 也需要加 `synchronized`；③ 写出按账户 id 排序加锁的转账模型。
- **什么情况属于尚未掌握**：每次进同步块都写 `synchronized (new Object())`（每线程一把新锁等于完全没锁）；或只给写方法加锁、读方法不加锁还以为能读到最新状态。
- **针对错误如何复习**：动手完成编程实验室 `s04-safe-counter`，重点测试 `get()` 与并发修改。
