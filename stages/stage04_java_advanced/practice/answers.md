# 预测与修改练习：答案

**先完成 [predict_and_modify.md](predict_and_modify.md) 再打开本文件。**

## S04A1
```text
执行线程：main
执行线程：worker
```
`fake.run()` 没有启动任何新线程——run() 是普通方法调用，任务在**调用者（main）**里同步执行完才返回。`worker.start()` 才真正新开执行流，任务在 worker 线程里跑。判断并发与否的试金石：`Thread.currentThread().getName()` 的值。两行的顺序是确定的：run() 同步执行完，start() 的调度才发生。

## S04A2
```text
出现过的执行者：[pool-1-thread-1, pool-1-thread-2]
不同执行者数量：2
```
corePoolSize=2 的池只有两条常驻工人线程；5 个任务排队轮流使用它们。执行顺序由调度与队列决定（任务 1/2 先上，3/4/5 排队补位），但**名字集合恒为这两个**——这正是"池化"的含义：线程数量有上限，任务数量没有。

## S04B1
恒为 200000。AtomicInteger 的 incrementAndGet 把"读-改-写"做成一条硬件级原子指令（CAS），三个步骤不可分割。volatile 版丢的更新没有"去哪"：两个线程同时读到同一个旧值，各自加一再写回，后写覆盖先写，一次加法被静默吞掉。

## S04B2
不成立——竞态回归，结果通常小于 2000。锁的对象决定互斥范围：两个线程必须抢**同一把锁**才会互相等待；`lock` 与 `otherLock` 是两扇互不相干的门，各进各的，临界区形同虚设。
