# HTTP 状态码实验：200、404 与连接失败

## 1. Scenario：从一个具体问题出发
监控里同时出现“接口 404”和“接口连不上”两种告警；如果用同一套重试和告警策略处理，要么掩盖故障，要么误报刷屏。

## 2. Why：为什么这个问题值得系统理解
404 是服务器给出的应用层应答（TCP 连接已建立、HTTP 响应已返回）；`ConnectException` 是传输层失败（三次握手都没完成，根本没有 HTTP 应答）。二者混为一谈，重试策略就会失真：404 重试通常无意义，连接失败则可能是瞬时故障。

## 3. Concept：核心概念
HTTP 应答由状态码分类：2xx 成功、4xx 客户端错误（404 资源不存在）、5xx 服务端错误。传输层失败的信号是异常（连接被拒、超时）而不是状态码。JDK 自带 `com.sun.net.httpserver.HttpServer` 可以在本机启动真实 HTTP 服务，配合 `HttpClient` 一次实验就能同时观察三种结果。

## 4. Mental Model：把机制装进一张图
`请求 -> [TCP 连接成功?] 否 -> ConnectException（传输层）`；`是 -> [服务器应答?] -> 200/404/5xx（应用层语义）`。层级不同，处理主体不同：连接失败归网络/容量，404 归路由或资源。

## 5. Minimal Code：最小示例
```java
// 本机真实服务：/health 返回 200，/missing 返回 404（完整示例见本课源码）
server.createContext("/health", exchange -> exchange.sendResponseHeaders(200, 2));
server.createContext("/missing", exchange -> exchange.sendResponseHeaders(404, 9));
// 服务停止后再请求 -> ConnectException，连状态码都没有
```

## 6. Observe：先预测，再运行
先预测三次请求各自的结果（200、404、连接异常），再运行源码核对三行输出。最后把 404 分支的路径改成 `/health2` 再请求，确认只要 TCP 通了，路径不存在也一定得到 404 而不是异常。

## 7. Modify：只改一个有意义的条件
把 `/health` 的响应改成 500，观察监控语义如何变化；或给 `HttpClient` 设置 1 毫秒超时制造读取超时，区分“连接被拒”与“连接后无应答”是两种不同的异常。

## 8. Exercise：独立完成
在本机实验基础上实现 `probe(String url)`：返回三种结果之一（`OK(200)`、`HTTP(状态码)`、`TRANSPORT(异常类型)`），并写明每种结果对应的重试/告警策略。不要在网络层吞掉应用层错误，也不要把 404 当作需要重试的故障。

## 9. Real Usage：联系 Java 与工程实践
健康检查、网关路由和第三方调用都需要区分应用层状态与传输层失败：重试连不上（配合退避）、告警 5xx、404 则排查路由或发布。这也是熔断器和重试框架默认策略的分层依据。
