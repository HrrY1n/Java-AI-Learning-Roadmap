# 拥塞控制：慢启动、AIMD 与公平性

## 1. Scenario：从一个具体问题出发
大量并发下载让共享链路抖动，单连接重试反而恶化。

## 2. Why：为什么这个问题值得系统理解
网络是共享资源；发送方需要根据丢包或延迟调整速率。

## 3. Concept：核心概念
AIMD 在无拥塞时线性增加，遇拥塞减半；慢启动指数探测。现代 TCP 还有 CUBIC、BBR 等实现差异。Java 应用通常通过库和 OS 栈受益，不直接控制拥塞窗口。

## 4. Mental Model：把机制装进一张图
`探测容量 -> 拥塞信号 -> 降低速率 -> 再次增长`。

## 5. Minimal Code：最小示例
```java
int cwnd = 1;
int ssthresh = 8;
for (int rtt = 1; rtt <= 16; rtt++) {
    if (rtt == 6) { ssthresh = cwnd / 2; cwnd = 1; } // 第 6 个 RTT 丢包（教学假设）
    else if (cwnd < ssthresh) cwnd *= 2;             // 慢启动：指数增长
    else cwnd += 1;                                  // 拥塞避免：线性增长（AIMD 的 AI）
    System.out.println("RTT " + rtt + " cwnd=" + cwnd);
}
```
这是纯算术教学模型：不发包、不测真实网络，只呈现窗口形状。

## 6. Observe：先预测，再运行
先在纸上画出 RTT 1-16 的 cwnd 折线（第 6 个 RTT 丢包后从 1 重新开始），再运行上面的循环核对形状：指数段、回落点、线性段是否都在预期位置。

## 7. Modify：只改一个有意义的条件
把丢包点从第 6 个 RTT 提前到第 3 个或推迟到第 12 个，观察回落后的恢复速度；再把 ssthresh 改成 16，比较慢启动段变长对总吞吐趋势的影响。

## 8. Exercise：独立完成
实现一个标注为模拟的拥塞窗口模拟器，不访问真实网络，并用它解释重试风暴。

## 9. Real Usage：联系 Java 与工程实践
限流、退避重试和队列积压处理应考虑共享链路的拥塞反馈。
