# 崩溃一致性：FSCK 与预写日志

## 1. Scenario：从一个具体问题出发
更新元数据和数据之间断电，文件系统可能指向错误块。

## 2. Why：为什么这个问题值得系统理解
多块写入不是原子操作；崩溃一致性要求协议先保证可恢复。

## 3. Concept：核心概念
FSCK 崩溃后扫描修复；日志先记录意图，再提交检查点，再应用变更。元数据日志常见折衷。

## 4. Mental Model：把机制装进一张图
`journal(TX begin, write, commit) -> checkpoint -> data`。

## 5. Minimal Code：最小示例
```java
// 教学模拟：一次文件更新 = 写数据块 D + 写元数据块 M，每个写步骤后都可能崩溃
// 协议一（无日志，先 M 后 D）：崩溃点 1 出现“M 指新块、D 是旧内容” -> 读到垃圾
// 协议二（无日志，先 D 后 M）：最多丢失更新，不会出现垃圾
// 协议三（预写日志）：BEGIN -> 记意图 -> COMMIT -> 应用 -> 恢复时按 COMMIT 决定重放或丢弃
```

## 6. Observe：先预测，再运行
先对每个崩溃点预测恢复后的文件状态：无日志两种顺序各 3 个崩溃点、预写日志 6 个崩溃点；再运行模拟器核对——只有预写日志在任何崩溃点都保证“旧值或新值，绝不出现垃圾”。注意协议一“先元数据后数据”的崩溃点 1 正是不一致状态的来源。

## 7. Modify：只改一个有意义的条件
把协议三的 COMMIT 提前到写意图之前（不合法的日志序列），或把恢复规则改成“无条件重放”，观察哪种崩溃点会破坏一致性，从而理解 COMMIT 点为何是分界。

## 8. Exercise：独立完成
实现一个纯内存日志模拟器，支持“崩溃后按日志恢复”；明确标注不是真实文件系统。

## 9. Real Usage：联系 Java 与工程实践
数据库 WAL、Redis AOF 和可靠写入流程都依赖类似思想。
