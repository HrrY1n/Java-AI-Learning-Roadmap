# Stage 02 练习

## 练习 1：银行账户守门

**任务背景**：为银行柜台程序实现一个 `BankAccount` 类。所有余额变化必须经过守门规则，任何非法操作都不能改变对象状态。

- **初始状态**：`new BankAccount("小明", 100.0)` —— 构造器同时校验初始余额不能为负。
- **菜单功能**（Scanner 循环）：
  1. 存钱：输入金额，金额必须大于 0；成功后打印 `存入后余额：200.0` 这样的结果。
  2. 取钱：输入金额，金额必须大于 0 且不超过余额；成功后打印取款后余额。
  3. 查询余额：打印 `小明 的当前余额：100.0`。
  4. 0 退出。
- **约束**：
  - `balance` 必须是 `private`，类外不得有任何直接改写途径；
  - 非法操作打印明确提示，**对象状态保持不变**，程序不崩溃；
  - 非数字输入不崩溃（Stage 01 的 Scanner 防御模式仍适用）；
  - 菜单循环、非法菜单项提示并回到菜单。

**示例（正常）**：初始 100 → 存 100 → 查询 → `200.0`。
**边界示例**：余额 100 → 取 100 → 成功，余额 `0.0`。
**错误输入（必须处理）**：存 `-50`、取 `99999`、输入 `abc`——分别提示，余额不变，程序继续运行。

**验收条件**
- [ ] 上述正常、边界、错误输入各运行一遍，行为全部符合预期。
- [ ] `balance` 为 private，且类中不存在绕过守门的公开写入口（不提供 setBalance）。
- [ ] 非法操作后打印的余额与操作前一致（状态未变）。
- [ ] 能解释：为什么把校验写在方法里，而不是指望每个调用者自觉检查。

**需要独立思考的部分**：取钱的两个失败条件（金额非法 / 余额不足）分别检查还是合并检查？给出你的选择与理由。

## 渐进提示（卡住才看，逐级解锁）

### 练习 1：银行账户守门

- **L1 理解问题**：这是一个“带守门规则的状态机”——余额是状态，存/取是受控的状态变更，规则决定变更是否发生。
- **L2 相关知识**：封装深化课（03_encapsulation_why）的 SafeAccount 就是本练习的最小骨架；Scanner 防御模式见 Stage 01 深化课 07。
- **L3 结构思路**：字段 `private double balance` + 构造器校验 → `deposit(double)` / `withdraw(double)` 内先校验后修改 → `showBalance()` 只读输出 → main 只做菜单循环与分发。
- **L4 调试线索**：非法操作后余额变了 → 检查是否先改了状态再校验；输入 `abc` 崩溃 → 坏记号没有被消费；取款判定写反 → 先打印"余额不足"分支的判断条件逐词核对。
