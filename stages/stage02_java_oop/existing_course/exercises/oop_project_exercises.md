## 方向 A：学生管理系统（对照 `src/student/`）

**任务背景**：教务处需要一个能增查改学生的最小系统，本期先做内存版（不存文件，那是 Stage 03 的练习）。

- **功能需求**
  1. `Student` 增加 `email` 字段（构造器赋值）。
  2. `StudentService` 支持按 id 查询、修改分数（分数必须在 0~100，否则失败）。
  3. 入口菜单：1 添加 / 2 按学号查询 / 3 修改分数 / 4 列出全部 / 0 退出。
- **输出示例**：查询命中 → `学号 2：小红，邮箱 xh@school.cn，分数 95`；未命中 → `学号 99：不存在`；改分非法 → `修改失败：分数必须在 0 到 100`。
- **约束**：业务规则不写在 main；Service 不出现 `Scanner`/`System.out.println`（返回数据，入口展示）。

**正常示例**：添加 → 查询 → 改分 95 → 再查询显示 95。
**边界示例**：添加两个相同 email 的学生（本版本允许，注释说明"email 唯一性留给后续"）；改分为 0 与 100（边界值必须成功）。
**错误输入**：菜单输字母不崩溃；改分为 -1 与 101 必须失败且程序继续运行。

**验收条件**
- [ ] 上述全部会话实际跑通；菜单防御与 Stage 01 练习 3 同标准。
- [ ] `Student` 的字段全部 private（[封装深化课](../../deep_dives/03_encapsulation_why/README.md) 的守门检查）。
- [ ] 指出参考实现 `src/student/` 的一个具体可改进点（对照你的实现说明取舍）。

**需要独立思考的部分**：`updateScore(int id, int newScore)` 失败时如何让调用方知道？返回 boolean / 抛异常 / 返回字符串消息——三选一并写一句理由（Stage 03 会给出更正式的答案，此处积累直觉）。

## 方向 B：图书借阅（对照 `src/library/`）

**任务背景**：图书需要记录"在馆/借出"状态，借还操作改变状态。

- **功能需求**：`Book` 增加价格字段与借阅状态；`LibraryService` 支持按书名查找、借书（已借出则失败）、还书。
- **输出示例**：借出成功 → `《Java核心技术》借出成功`；重复借 → `失败：该书已借出`。
- **约束**：状态字段 private，只能通过 `borrow()/giveBack()` 改变；找不到书要有明确提示。

**正常示例**：加书 → 借 → 还 → 再借。
**边界示例**：同名多本书，按书名借出的行为要明确定义（借第一本？拒绝？——你定义规则并在注释里写清）。
**错误输入**：借不存在的书；还未借出就还书。

**验收条件**
- [ ] 借-还-再借全流程跑通；两种错误输入都有明确提示且不崩溃。
- [ ] 能解释"为什么状态字段不能 public"（用 [引用深化课](../../deep_dives/01_reference_state/README.md) 的别名问题举例）。
- [ ] 与 `src/library/` 对照：借书失败的判断在哪个类里？你的版本一致吗，为什么？

**需要独立思考的部分**：`borrow` 失败是"常规分支"还是"异常情况"？这决定了你用返回值还是异常（Stage 03 深化课 03 的前置思考）。

## 方向 C：银行转账（对照 `src/bank/`）

**任务背景**：转账是"一次业务动作改两个账户"的最小样本，是理解事务的种子。

- **功能需求**：`BankService.transfer(from, to, amount)`——余额充足则两边同步变化；不足则**两边都不变**。
- **输出示例**：`转账成功：A001 -> A002 金额 300.0`；失败 → `转账失败：余额不足`。
- **约束**：金额必须 > 0；`Account` 字段 private；失败路径必须保证"两个账户状态一致"。

**正常示例**：500 → 转出 300 → A001 剩 200、A002 多 300。
**边界示例**：转出全部余额（正好清零）应成功；转 0.01。
**错误输入**：金额为负；余额不足。

**验收条件**
- [ ] 成功与失败两条路径下，两个账户的余额都能被验证一致。
- [ ] 能回答：为什么"先扣 from 再加 to"失败在中间时，问题比"余额不足"严重得多？（为 Stage 05 事务埋种子）
- [ ] 与 `src/bank/` 的 `transfer` 对照失败分支的写法。

**需要独立思考的部分**：`transfer` 里先校验"总额够不够"再动手，与"先扣再退回"两种实现，哪个更容易写对？为什么？

## 渐进提示（卡住才看，逐级解锁）

### 方向 A
- **L1 理解问题**：三个功能都围绕"按 id 找到那个对象"；先写 `findById` 并让它返回"找不到"的明确信号。
- **L2 相关知识**：对象别名与 == 见深化课 01；Service 返回数据不打印见深化课 06。
- **L3 结构思路**：Student（字段+校验）→ StudentService（列表 + 三个方法）→ App（菜单循环，只组装展示）。
- **L4 调试线索**：改分后查询还是旧值 → 你改了副本（检查是否 new 了新对象而非改原对象）；菜单死循环 → 坏记号没消费。

### 方向 B
- **L1**：书的本质是"信息 + 状态机"（在馆 ⇄ 借出）；先把两个状态的转换规则列出来再写代码。
- **L2**：状态封装见深化课 03 的窗口模型。
- **L3**：Book.borrow() 返回成功与否（状态转换规则内聚在 Book）；LibraryService 负责找书并调用。
- **L4**：还书后又还一次成功了 → giveBack 里漏了"当前必须已借出"的判断。

### 方向 C
- **L1**：转账 = 有条件的双向改数；先在纸上写出成功/失败时四个余额值。
- **L2**：引用传递决定了"方法内改账户字段 = 改真账户"（深化课 01）。
- **L3**：transfer：参数校验 → 查 from 余额 → 同时改两边 → 返回成功描述；任一前置失败直接返回失败描述。
- **L4**：失败后 from 被扣了 → 你的扣款发生在校验之前；金额 0.1+0.2 类误差 → double 比较别用 ==，先想清楚这版练习是否接受。
