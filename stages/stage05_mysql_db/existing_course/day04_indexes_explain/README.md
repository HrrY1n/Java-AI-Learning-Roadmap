# 索引、B+ 树原理与 EXPLAIN 分析

> 对应示例：`day04_indexes_explain/App.java` · 目标版本：**MySQL 8.0 InnoDB**

## 1. 为什么加了索引查询能从扫描几万行降到几次比较？

没有索引时，`WHERE dept_code = 'D3'` 必须从第一行扫到最后一行（`type = ALL` 全表扫描）。在 InnoDB 中，索引是一棵**矮胖的多路平衡查找树（B+ 树）**：非叶子节点只存索引键与子页指针（一页 16KB 能存上千个指针，千万行数据也只需要 **3~4 层**树高），所有数据都按索引键有序挂在叶子节点链表上。

### 聚簇索引 vs 二级索引（“回表”与“覆盖索引”）

- **聚簇索引（主键索引）**：叶子节点直接存着**整行数据**，按 `id` 查找一次 B+ 树即拿到整行（`type = const`）。
- **二级索引（普通/联合索引）**：叶子节点只存**索引列的值 + 对应的主键值 `id`**。因此 `SELECT id, username WHERE dept_code = 'D3'` 需要先查二级索引拿到 `id`，再拿 `id` 回主键树取 `username`——这叫**回表**。
- **覆盖索引（`Extra: Using index`）**：如果你查询的列刚好全部被 `(dept_code, score)` 和主键 `id` 包含（如 `SELECT id, dept_code, score ...`），优化器直接从二级索引叶子拿走结果，**无需回表**！

## 2. 联合索引与最左前缀原则

建立联合索引 `INDEX idx_dept_score (dept_code, score)`，B+ 树先按 `dept_code` 排序，`dept_code` 相同的再按 `score` 排序。因此：
- `WHERE dept_code = 'D3' AND score >= 80`：先精确定位 `'D3'`，再在 `'D3'` 段内有序范围查找 `score >= 80` → **命中索引**！
- `WHERE score >= 80`：跳过最左列 `dept_code`，整棵树里 `score` 并不是全局有序的 → **无法走这棵索引树，退回 `ALL`**。

## 3. 让索引失效的四大高频错误

1. **在索引列上套函数或做算术**：`WHERE LOWER(dept_code) = 'd3'` 或 `WHERE score + 10 >= 90` —— 树里存的是原始值，优化器找不到对应键，直接全表扫描。
2. **`LIKE '%关键字'` 前导通配符**：`LIKE 'user_%'`（前缀确定）可用索引，而 `LIKE '%_10'`（前导 `%`）退回全表扫描。
3. **隐式类型转换**：字符串类型字段传数字 `WHERE student_no = 2026001`（无引号），MySQL 会隐式转成数值比较，等同于在列上包了一层转换函数！
4. **`OR` 两边未全覆盖索引**：一边有索引、另一边无索引时常退回全表扫描。

## 4. 怎么看懂 `EXPLAIN`（最核心 4 列）

- **`type`**：性能大致顺序 `const`（主键等值）> `ref`（非唯一索引等值）> `range`（索引范围）> `index`（全索引扫描）> **`ALL`（全表扫描，报警！）**。
- **`key`**：实际选用的索引名；为 `NULL` 说明根本没走索引。
- **`rows`**：优化器估算需要扫描的行数（越少越好）。
- **`Extra`**：`Using index`（覆盖索引，极好）；`Using filesort` / `Using temporary`（额外排序/临时表，需警惕）。
