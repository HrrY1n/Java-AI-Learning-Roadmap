# 关系模型、外键与多表连接

> 对应示例：`day02_relational_modeling/App.java` · SQL 脚本：`sql/02_relations_and_joins.sql`

## 1. 怎么拆表才不造成更新异常？

如果把学生姓名、课程名、学分、成绩全部塞进同一张大宽表里，每当一门课改名或换学分，你必须去改几百条选课行——漏改一行数据就不一致。关系建模按实体关系拆分：
- **一对多（1:N）**：在“多”的一侧放指向“一”的一侧的主键外键（如 `orders.user_id` 指向 `users.id`）。
- **多对多（M:N）**：一个学生选多门课、一门课有多个学生——**建中间表 `lab_enrollments`**（存 `(student_id, course_id)` + 唯一联合键防重复选课，以及选课成绩 `grade`）。

## 2. 外键与互联网工程取舍

- **`ON DELETE RESTRICT`**（默认安全策略）：如果某学生还有选课记录，直接删除该学生会报错拦截，避免留下“孤儿选课记录”；插入不存在的 `student_id = 9999` 也会抛 MySQL 错误码 **`1452`**。
- **`ON DELETE CASCADE`**：删主表记录时顺带把子表全删光——极度危险，误删一个用户可能连订单流水一起蒸发，生产极少直接用级联删除。
- **物理外键 vs 应用层校验**：在中大型高并发或分库分表系统中，团队常不在数据库建物理外键（减少写锁争用与架构变更耦合），而是在 **Service 层逻辑校验 + 唯一索引 + 定期对账** 保障一致性——但作为入门，先用物理外键理解参照完整性是最佳路径。

## 3. `INNER JOIN` vs `LEFT JOIN` 与两大致命陷阱

| 连接方式 | 结果集合 | 什么时候用 |
| --- | --- | --- |
| `INNER JOIN` | 只返回左右两表在 `ON` 条件**都匹配**的行 | 只关心“已选课的记录” |
| `LEFT JOIN` | **左表全部行必然保留**；右表没匹配上的行右侧列填充 `NULL` | 查“全部学生及选课情况（含未选课者）” |

1. **漏写 `ON` 或条件写错导致笛卡尔积爆炸**：两张 1 万行表误做无条件交叉连接会产生 1 亿行，直接打死数据库。
2. **`LEFT JOIN` 的过滤条件错放进 `WHERE`**：想“列出所有学生及其 JAVA101 成绩（没选的保留行显示 NULL）”，若把 `c.course_code = 'JAVA101'` 写在 `WHERE` 里，`NULL != 'JAVA101'` 会把未选课的学生全过滤掉，**`LEFT JOIN` 瞬间退化成 `INNER JOIN`**！**规则**：限制右表保留哪些匹配项必须写在 `LEFT JOIN ... ON ... AND c.course_code = 'JAVA101'` 里，`WHERE` 只放对主表的筛选或 `IS NULL` 判未匹配。

## 学习验收与自我检核

- **需要掌握什么**：把 1:N 与 M:N 场景拆成规范表结构；理解 `INNER JOIN` 与 `LEFT JOIN` 差异及外键约束含义。
- **如何证明理解**：① 写出“只保留所有学生，且只关联 DB201 课程”的 `LEFT JOIN` SQL（不退化为内连接）；② 统计每名学生选课门数（未选课显示 `0`，提示：`COUNT(e.id)` 而不是 `COUNT(*)`——因为左连接产生的 NULL 行用 `COUNT(*)` 会错误算成 `1`！）。
- **什么情况属于尚未掌握**：对 M:N 关系在两张表各建一个逗号拼接字符串字段 `course_ids = "1,2,3"`；或以为 `LEFT JOIN` 只要写了关键字就一定保留左表全部行。
- **针对错误如何复习**：对照执行 `sql/02_relations_and_joins.sql` 观察两段 SELECT 的行数差异；试把 `AND` 过滤移入 `WHERE` 实测退化现象。
